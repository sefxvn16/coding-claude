# Build, merge, cleanup (steps 4-6)

- Parallel builders: give each independent module (disjoint files in the ownership table) its own `coding-claude:builder` and handoff `04-handoff-<n>.md`, and launch all ready builders in ONE message so they run concurrently, each in its own worktree. The number of builders = the number of modules that do not need another module's result; a dependent module starts after its dependency is merged (its START = the new tip). Every parallel builder runs its own `setup`, so count that time and usage when choosing how many to launch. Builders run on Sonnet; pass `model: opus` for a module the architect marks hard (tricky algorithm, concurrency, security-sensitive) and say why in one line.
- Worktree and START: a builder runs in `<repo>/.claude/worktrees/agent-<id>` (isolation: worktree), creates its own branch `cs/<task-id>-<n>` at START, commits there and reports branch + hash. START is in the handoff: the current tip of `cs/<task-id>` when you write it (equal to BASE for the first builder; once earlier task commits or builder merges exist, START is that newer tip, so the second builder does not conflict with them). BASE stays the task's original base and is only used for verify and review. Record the builder's agent id from the Agent result in its handoff file. A subagent worktree starts from the repository's default branch unless the setting `worktree.baseRef` is `"head"`; the builder moves to START itself. If the builder reports the START commit is missing, stop. Claude Code copies the gitignored files listed in the project's `.worktreeinclude` into the worktree. Uncommitted work does not come back.
- Builder ended without DONE (BLOCKED, FAIL, timeout, turn limit, no reply): read `builder-recovery.md` before any new delegation.
- Merge, in the main checkout on `cs/<task-id>`: for each builder branch `git merge --no-ff <branch>` (or cherry-pick). If a conflict still happens, resolve it yourself only in glue code, otherwise send it back to the owning builder (rebased on the new tip).
- Cleanup, per builder, only after its merge succeeded (for a retried builder, also clean the replaced builder's worktree and branch once the retry's branch, which contains its commits, is merged): `git worktree remove <path>` (no `--force`; if it refuses because the worktree is dirty, report to the owner); then `git branch --merged cs/<task-id>` must list the builder branch, and only then `git branch -d <branch>`. The harness also leaves a branch `worktree-agent-<id>` per worktree: after the worktree is removed, check `git branch --list 'worktree-agent-*' --merged cs/<task-id>` and delete the listed ones with `git branch -d`. Never `git branch -D`. These commands are not gated by this plugin; your global ask rules may prompt.
