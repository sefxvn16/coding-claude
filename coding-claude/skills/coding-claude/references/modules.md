# Modules, scope and locks (only when `.studio/modules.json` exists)

The registry (template `templates/modules.json`) is the project's lasting map: each module has `paths` (globs; a file belongs to at most one module; a directory is `dir/**`), `public` (files other modules may import; empty = any), `depends_on` (modules it may import), `status` `open` or `locked`, and optionally `optional: true` with `off_test` (a module that can be switched off; a required module may not depend on it); `dependency_check` is `off`, `warn` (default) or `block`. It is owner-controlled config: you never change it on a task branch (the verifier refuses with CONFIG-ERROR). Unlock, lock, move paths or change `public`/`depends_on` only on the owner's word, as its own commit on the integration branch BEFORE BASE; a change of `public` or `depends_on` is a public-interface change (M2).

- Intake (before BASE): the registry must be committed like project.json; run the module audit script once (exit 2 = invalid or overlapping registry: stop and tell the owner). Name the modules the task needs. A needed module is `locked`: stop and ask the owner to unlock it before BASE is recorded.
- Scope: before the first builder, save `work/<task-id>/scope.json` (template `templates/scope.json`): `modules` the task may change plus `files` globs for anything else it needs (new tests, docs, files in no module, the touched specs). Keep it as small as the brief allows, but include companion files the change will commit outside the module globs (lockfiles, generated `.uid`/`.import` files, snapshots); copy it into every handoff. Files created by the project commands during verify are ignored. Widening it after M1 needs the owner when it adds a module.
- Enforcement: the `protect-checks` hook denies every agent an edit inside a `locked` module, denies the builder an edit outside the scope of its branch (`cs/<task-id>` or `cs/<task-id>-<n>`, scope read from `work/<task-id>/scope.json` of the main checkout) and warns you. The verifier, run with `--scope`, FAILs on any changed file outside the scope or inside a locked module, also for shell writes no hook sees.
- Out-of-scope finding (a bug or needed change in another module): do not fix it in this task. Record it in `PLAN.md` as a new item with evidence and tell the owner; if the task cannot finish without it, stop and ask (widen scope, or do the other task first).
- Dependency check: imports found by path (`preload`/`load`/`res://` in Godot files, relative `import`/`require` in JS/TS) in changed files are checked against `depends_on` and `public`; only violations the task added count (those already in the file at the merge-base are ignored; the audit script lists the old debt). Not seen: GDScript `class_name` globals, TS path aliases, Python; for TS/Python prefer the project's own boundary linter in `commands.lint`. `warn` gives PASS-FLAGGED (judge every flag), `block` gives FAIL.
- Design: for a new project, a new feature area, or code that grew too big (signals in the audit: largest and most changed files), give the architect the absolute path of `references/modular-design.md`: core + ports, switch-off and replacement rules, and the step-by-step split. A split is its own task proposed to the owner, never part of an unrelated one.
- No registry yet: do not invent one inside a task. Propose it to the owner (init step, or architect DESIGN for a split); the audit script checks a draft (unowned files, dependency map, violations).
